# ADR-0004：批量编译的切块策略与「批次中断」处理

- 状态：已采纳（2026-10-20）
- 影响范围：`harness/runner.py`、`harness/leanenv.py`、`harness/cli.py`

## 背景

harness 的核心性能手段是**把同一轮的题拼进一个 Lean 文件编译**，因为成本主要由
`import Mathlib`（约 240 s）决定，与文件里有多少道题几乎无关（ADR-0001 的实测）。

2026-10-20 跑 244 题 Valid 基线时，这个假设被打破：

- 一次编译跑了约 750 s；
- 但**只有前 110 题有诊断输出**，后面 133 题一条 `error`/`warning` 都没有；
- 这 133 题被记成 `status=failed`，`error_types` 为空——**看起来像「证明失败」，
  实际是根本没被 Lean 处理**。如果不发现，就会得出「L0 只有 9/244」的错误结论。

## 根因（2026-10-20 深夜定案）

**`maxErrors` 的默认值是 100。** Lean 攒够 100 个错误就直接退出：

```
...: error: maximum number of errors (100; from option `maxErrors`) reached, exiting
```

退出之后，文件里后面的声明**完全不会被处理**——所以「后 133 题一条消息都没有」，
不是崩了，不是卡了，是 Lean 自己收工了。244 题单批次恰好停在 ~110 题，
数量上也对得上（前 110 题累计 100 个错误）。

两条弯路先记在这里，避免重犯：

1. 一开始怀疑是「某一题把 Lean 带崩」，用 20 题切片复现却完全正常——因为切片里
   错误总数不到 100，根本没触发退出。
2. 后来发现超长定理名会让 `#print axioms` 折行、解析器认不出（另一个独立 bug），
   一度以为那才是主因。它确实造成 1 题误判，但**不是** 133 题消失的原因。

### 修复

在命令行上加 `-DmaxErrors=0`：

```
lake env lean -DmaxErrors=0 <file>
```

**注意**：写在文件里的 `set_option maxErrors 0` **无效**。实测同一份 120 个错误的文件：

| 写法 | 报出的错误数 | 是否退出 |
|---|---:|---|
| 默认 | 100 | 是 |
| 文件内 `set_option maxErrors 0` | 100 | 是 |
| 命令行 `-DmaxErrors=0` | 120 | 否 |

所以这条只能在 `harness/leanenv.lean_argv()` 里保证，不能靠题目文件。

### 配套：墙钟超时才是硬兜底

关掉 `maxErrors` 之后，失败证明会被**完整执行**，于是又暴露出另一头：
一份模型批次跑了 30 分钟还没结束（lean 进程吃 5 GB 内存、持续占 CPU）。

中途试过用 `maxHeartbeats` 限制，**单位搞错了一次**：Lean 的 `maxHeartbeats` 单位是
「千次心跳」，`300000` 意味着 3 亿 tick 而不是 30 万，于是「限制」等于没限。
而且实测 `set_option maxHeartbeats 1` 也没能中断一个平凡证明，说明它不适合当兜底。

最终方案：**按墙钟超时**（`config.COMPILE_TIMEOUT_S`，默认 1800 s）。
超时后 `compile_file` 返回 `returncode=-1`，runner 把该块所有题标成
`status=error` + `error_types=["batch_timeout"]`，然后**继续下一块**。
这样病态批次最多损失一块，不会让整轮挂死，也不会污染成「证明失败」。

## 已知事实与未知

**已知**：
- 488 题全部用 `sorry` 做语句编译（compat scan）时正常，说明不是语句本身的问题；
- 把出问题位置附近 20 题单独编译（`--slice 105:125`）**完全正常**，20 题都有诊断，
  其中 6 题 verified。所以不是某一题单独致命；
- 失败发生在「244 题 + 全量 cascade」这种规模下，20 题规模下不复现。

**根因（2026-10-20 当天补齐）**：真正的原因不在 Lean，而在**解析器**。
第一版运行的那次里，`#print axioms` 因定理名过长被折成多行，解析器要求整条在一行，
于是这些题拿不到公理报告，又被「无诊断 + 无公理报告」的启发式判成没跑过。
也就是说：

* 那 133 题里**大部分确实被 Lean 处理了**，只是判定层把它们误标成失败；
* 「后 133 题全没诊断」这个观察本身也可能是输出缓冲/记录方式造成的假象。

用一个 20 题的切片复现时完全正常，就是因为切片里没有那种超长名字。

结论：**这是两层 bug 叠加**——(a) 解析器对折行不健壮，(b) 判定层用「没有公理报告」
去推断「没跑到」，而前者会让后者误触发。

## 决策

三条一起做，缺一不可：

1. **切块编译**（`--chunk-size`，默认 60）。
   把一整个 split 拆成若干块，每块独立编译。爆炸半径限制在一块之内，
   而且能定位到是哪一块出的问题。

2. **保留每一块的原始编译器输出**（`runs/<work_name>.lean.log`）。
   下次再出现中断，可以直接看日志里最后一条消息，而不是靠猜。

3. **区分「失败」与「没跑到」**。
   `_apply_audits` 里：如果某题**既没有诊断、也没有 `#print axioms` 报告**，
   判定为 `status=error`、`error_types=["batch_truncated"]`，而不是 `failed`。

## 后果

- **好处**：244 题的统计不再可能被静默污染；出问题时能定向复现。
- **代价**：成本从「1 次 Mathlib 载入」变成「块数 × 载入」。
  244 题按 60 切块 = 5 块 ≈ 5 × 4~5 min（原来 1 块 ≈ 12 min）。
  这是用约 2~3 倍的编译时间换统计正确性，值。
- **补丁**：`scripts/reaudit_run.py` 可以用保存下来的批次文件 + 日志**离线重算**
  一次运行的判定，重算前逐字节比对批次文件。以后修判定逻辑不必重跑几个小时。
  代价是重算会把 `time_ms` 置零（本来也只是共享上界）。

## 仍待确认

- 那次运行的原始输出里，133 题到底是「全部跑了但解析丢了」，还是「真的中途没跑」。
  当时没有落盘日志，无法回溯。**现在每块都有 `.lean.log`，同样的现象下次可以直接查。**

## 触发下一步的条件

如果切块后仍有块出现 `batch_truncated`：
1. 先看该块的 `.lean.log` 最后 200 行；
2. 用 `--slice` 二分该块（每次约 4~5 min）定位到单题；
3. 若是解析问题，先修 `harness/diagnostics.py` 并补一条回归测试；
   只有确认是 Lean 真的中断，才考虑 `maxHeartbeats` 预算。
